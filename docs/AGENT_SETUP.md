# Agent Setup

Date: 2026-06-08

Truth Harness exposes a local stdio MCP server so Claude, Codex, and other MCP clients can ask for proof receipts, persisted verifier routes, benchmark runs and comparisons, local source search, structured local literature records, notebook-run provenance records, policy-gated direct code-run records, encrypted vault metadata, evidence audits, workspace validation and repair, workspace provenance snapshots, local model-context packets, external-call disclosure records, local simulation and experiment evidence, and private discovery logs.

## Build First

Default verification is Docker-first:

```bash
npm run verify:default
```

Use that before claiming the tree is ready for reviewer/demo work. It runs the no-network Docker engine smoke and then the full build/test suite inside compose. If Docker Desktop is not reachable, report that blocker explicitly. `npm run verify:native` and `npm run check` can help during development, but they are not the public credibility gate.

```bash
npm install
npm run build
```

The server entrypoint is:

```bash
node packages/mcp-server/dist/index.js
```

## Tools

Agents should call `truth_harness_engine_plan` first when opening a serious proof, SMT, CAS, code, simulation, source, or engineering subclaim. The plan is a read-only routing contract: it classifies the problem, selects the relevant verifier stack, compares the local engines that could support the claim, exposes blocked stronger gates, and recommends the first durable command. It does not run engines and cannot mint evidence. If the workspace contains saved strict Docker reviewer evidence, the plan may show that a prior no-network reviewer run covered Maxima, SageMath, Lean, Z3, and cvc5; treat that as routing memory only. A missing host Lean/Z3/Maxima/Sage command is still missing for the current action, and every new claim still needs its own concrete receipt, proof-check, SMT, CAS, source, or validation artifact. Call `truth_harness_engine_manifest` when the agent needs the full readiness and trust-boundary map: it can say which capabilities are ready, missing, planned, or safety-gated, but the manifest itself is not evidence for a claim. Use `truth_harness_verify` when an agent needs both a receipt and a verifier route/gap ledger; set `write: true` when the route should become a durable local artifact under `.truth-harness/routes/`. Leave `requireIndependentSmt` false for ordinary routes where one concrete SMT solver record is enough; set it true when a reviewer wants separate Z3 and cvc5 solver obligations. Then use `truth_harness_route_list`, `truth_harness_route_show`, and `truth_harness_route_satisfy` as the local work loop: find open or critical-open obligations, attach accepted local evidence, and only promote the claim after the route readiness says it is ready for a narrow claim. A ready narrow claim may still have open upgrade obligations; those are requirements before stronger labels, not evidence against the current conservative label. Formal-proof obligations require accepted proof-check records scoped to the exact route id and obligation id; do not attach a generic accepted Lean file to an unrelated route. Backend-specific SMT obligations require matching solver evidence, so a Z3 obligation needs a Z3 SMT-check record and a cvc5 obligation needs a cvc5 SMT-check record. If `workspace run-next --execute-local` sees that the selected host SMT backend is missing or blocked, it stops before writing retry noise and returns the Docker CLI command that should produce the concrete evidence instead. A not-ready `route:` ref stays attached to claim records as unverified evidence and becomes a finalization blocker. When a hard-problem session has a linked validation plan, `workspace run-next` ranks matching ready verifier routes as candidate gate evidence before generic claim recording, so an agent should attach the route to the open gate before filing the narrow claim. When recording a new claim from a verifier route, run-next now carries route-derived domain metadata such as `math`, `physics`, or `sources` instead of falling back to generic keyword inference. Use `truth_harness_validation_gate_attach` to attach `route:`, `receipt:`, `proof:`, `smt:`, `cas:`, `benchmark:`, `source:`, or `literature:` evidence to the exact open gate. The tool parses supported artifacts through the same validators as the CLI; it can satisfy, block, or keep the gate open with required next checks, but it cannot upgrade trust by assertion. Use `truth_harness_ask` when a receipt alone is enough.

For a compact reviewer workout, first call `truth_harness_workspace_hard_math_seed_list` with `preset: "professor-challenge"`, `latest: true`, and `handoff: true` to see whether the workspace already has a staged seed packet plus a Markdown reviewer packet. If no seed exists, call `truth_harness_workspace_seed_hard_math` with `preset: "professor-challenge"` before letting an autonomous agent roam. The same preset is available as `truth-harness workspace seed-professor-challenge .`, and saved packets can be reopened with `truth-harness workspace hard-math-seeds . --preset professor-challenge --latest`. For a copyable CLI handoff, run `truth-harness workspace hard-math-seeds . --preset professor-challenge --latest --handoff`; the Markdown packet names the seed files, run-next files, first gate, evidence need, stop rule, restore command, and next verifier command. It creates five linked validation-plan sessions covering a false parity refutation, exact fraction arithmetic, symbolic CAS closure, bounded SMT closure, and a Lean proof-checker boundary. Agents should then call `truth_harness_workspace_run_next` and close the selected gate with concrete local evidence instead of inventing generic progress.

For proof repair, do not rerun a rejected Lean proof check blindly. Workspace review records the failed proof attempt, diagnostic snippet, source path, source SHA-256, current source status, and, when the proof-check record exposed it, the exact declaration id/signature metadata on `proofAttempt.declaration`. Dry-run `workspace run-next` handoffs surface the same proof source state in `execution.kind` and `execution.summary` before local execution is attempted. If `workspace run-next --execute-local` sees that the selected failed proof source is byte-for-byte unchanged, it blocks before running Lean and tells the agent to edit the source first. If the source changed, rerun the scoped proof check to create fresh evidence. That keeps autonomous loops from creating duplicate failed proof artifacts.

Before an agent presents a ledger claim as usable, call `truth_harness_claim_review`. It returns a read-only review packet with `reviewStatus`, conservative decision text, blocking checks, evidence refs, next actions, and local CLI commands. Treat any status except `ready` as a stop sign for final claims; continue gathering evidence, narrow the wording, or label the result unverified/refuted.

## Security Notes

- The MCP server is local stdio only.
- Benchmark, receipt, source, and workspace paths are restricted to the workspace root.
- Write-capable tools only write local workspace artifacts under `.truth-harness/`.
- `truth_harness_workspace_credibility_actions` computes the same reviewer posture as a credibility pack but returns only the unresolved action queue. It is read-only, local-only, and should be the first MCP call when an agent needs to know which validation, engine, benchmark, or workspace-review blocker to close next. Professor-readiness benchmark actions include both the `ai-failure-seed` adversarial suite and the 30-case `math-credibility-ladder` hard-math readiness floor; run-next can execute either writable benchmark run through core APIs without shell execution.
- `truth_harness_workspace_credibility_bundle` accepts `requireAllEngines: true` for strict reviewer bundles that require Maxima, Z3, cvc5, Lean, and SageMath fixture evidence. Use it for external review packets, not for every fast local iteration.
- `truth_harness_verify` with `write: true` stores a local `truth-harness.verifier-route.v0` JSON record plus Markdown report under `.truth-harness/routes/`; `truth_harness_route_list` and `truth_harness_route_show` expose those records for agents, audits, claim ledger refs, validation plans, snapshots, and reports. Set `requireIndependentSmt: true` only when the route should require separate Z3 and cvc5 solver evidence. A route explains verifier selection and missing gates; it is not a proof by itself.
- `truth_harness_source_ingest` skips `.truth-harness/` so private logs and indexes are not accidentally re-ingested as source material.
- `truth_harness_workspace_validate` checks the root workspace manifest's private-by-default policy, receipt trust-boundary metadata, JSON Schema contracts, artifact ids, resolvable local evidence refs, and sent/received external-context approval/disclosure linkage for known workspace JSON records; it does not prove the validated claims are true.
- `truth_harness_catalog_search` accepts `ref` for reverse citation lookup. Use it before mutating or superseding a local artifact to find indexed reports, claims, snapshots, reviewer packets, visuals, and handoff records that cite the artifact; this is dependency/impact navigation, not evidence that any cited claim is true.
- `truth_harness_workspace_run_next` now carries the same idea into handoffs: when the selected action references local artifacts and the catalog is fresh, inspect `impactRefs` before acting. They show downstream artifacts that cite the selected evidence so an agent can avoid breaking reports, reviewer packets, or dependent claims silently. When possible, run-next also derives a `revalidationQueue` from those impact refs; follow those review commands before mutating or relying on the cited evidence, but do not treat the queue itself as proof or a trust upgrade.
- CLI agents can use `truth-harness workspace run-next <workspace> --json`, and MCP agents can use `truth_harness_workspace_run_next`, to get the next autonomy-contract work item as a dry run. In hard-problem harness workspaces, run-next discovers linked validation plans from research-session evidence refs, checkpoints, and plan provenance, then prioritizes open validation gates before generic session tasks so agents attack proof/evidence blockers first. If the linked session already contains candidate proof/SMT/CAS/route/source evidence for an open gate, that candidate becomes the concrete `truth-harness validation attach ... --evidence kind:ref` next command instead of a vague reminder to inspect the session. When a validation claim is already a narrow machine-checkable seed boundary, workspace review skips broad natural-language verification and emits the concrete verifier action instead: `truth-harness smt check docs/examples/constraints.smt2 --query bounded_integer_sat --write`, `truth-harness cas check --operation simplify --expression "sin(x)^2 + cos(x)^2" --result 1 --write`, or `truth-harness proof check docs/examples/lean-fixture/TruthHarnessFixture/Trivial.lean --declaration smoke --statement <claim> --write`. If a proof gate already has weak or unverified attached evidence, do not repeat the same broad verifier forever: run-next either lets concrete route obligations lead or returns an explicit stronger-engine boundary such as `npm run docker:engines`, `npm run docker:sage`, or `docker compose run --rm lean-proof`. If a blocked claim already has an equivalent ready verifier route, workspace review emits `truth-harness claim add ... --supersedes <claim> --evidence route:<route>` and bounded run-next execution writes that superseding claim through the claim-ledger API. Every run-next plan includes a `rationale` object with the selected target, source queue item, candidate evidence ref, execution boundary, first stop condition, and first warning; agents should read this field before acting instead of reverse-engineering intent from prose. When local `.truth-harness/...` files are involved, run-next also exposes `artifactRefs` with a path, role, source, and, when the file exists at handoff/list/read time, `sizeBytes`, `sha256`, `sha256Scope: "file"`, and a copyable `citation`; use those refs for artifact inspection and reviewer citations instead of scraping markdown tables or shell strings. When the selected item contains a scoped claim, `proof check --statement`, `cas check --expression`, source query, or `verify` route, the same packet also embeds an `enginePlan` object with the classified problem, recommended first durable command, verifier stack, blocked stronger engines, evidence requirements, and trust-boundary warnings. Treat `enginePlan` as routing guidance only: it does not run engines, mint receipts, or upgrade trust. If the workspace is genuinely idle, the plan remains `blocked` with `execution.kind: "no-open-item"` and includes `idleNextActions`: start a new validation-backed research harness, refresh the strict all-engine Docker professor rehearsal, refresh the lighter Docker professor reviewer rehearsal, refresh the professor credibility packet from saved evidence, or refresh the strict release audit. Treat those as local next-step options, not evidence of a solved claim; Docker professor actions are marked human-input-required because they start npm/Docker and run-next will not execute them automatically. Add `--source credibility-actions` or MCP `source: "credibility-actions"` when the next item should come from the professor credibility action queue instead of the general workspace review queue. Add `--write` or MCP `write: true` before handoff when the plan itself should become a durable local intent packet; the writer also records a source workspace snapshot created immediately before the packet. Reopen persisted handoffs later with `truth-harness workspace run-nexts`, `truth-harness workspace show-run-next <wrn_id>`, MCP `truth_harness_workspace_run_next_list`, or MCP `truth_harness_workspace_run_next_show`; list summaries expose the rationale target, source, candidate evidence ref, execution boundary, artifact refs, source snapshot ref, engine-plan status, engine-plan classifications, proof-repair target summary when present, and `resumeDecision` so an agent can triage many saved packets before loading the full plan. The web UI mirrors this split: opening a saved handoff is fast and read-only, while the explicit Verify action runs the heavier source-revision/source-snapshot check before any resume command should be trusted. Use `truth-harness workspace run-nexts --verify-snapshots` or MCP `verifySnapshots: true` before resuming old handoffs; verified summaries can mark `resumeDecision.safeToResume: true`, while drifted or unchecked summaries return a recovery command. Use `truth-harness workspace show-run-next <wrn_id> --verify-snapshot` or MCP `truth_harness_workspace_run_next_show` with `verifySnapshot: true` to verify one exact handoff packet before acting. Agents should only resume the saved selected command when `resumeDecision.safeToResume` is `true`, and otherwise follow the provided recovery command. A verified idle packet with no selected command returns `resumeDecision.status: "choose-idle-action"` so an agent must choose one idle action explicitly instead of treating an action menu as executable work. The check labels saved packets as `verified`, `drifted`, `missing`, or `not-recorded`, ignoring only the handoff JSON/Markdown files created after the source snapshot while still flagging real workspace drift. Use `--execute-local` or MCP `executeLocal: true` only for bounded local work: the shared core planner parses the queued `truth-harness ...` command, rejects shell metacharacters and placeholder paths, and calls supported core APIs in-process for claim reviews, route/session/report reads, proof checks, SMT checks, CAS checks, concrete `validation attach` commands, verifier-route writes for validation proof gates, claim-add closure actions that cite ready route evidence, writable engine verification runs, and writable benchmark runs. When verifier-route evidence, direct proof/SMT/CAS artifacts, or a concrete validation attachment targets a linked validation gate, the plan is updated conservatively: exact-computed/cross-checked/smt-checked/proved evidence satisfies a proof gate only when scoped to the validation claim, refuted evidence blocks it, and unverified, missing-engine, or unscoped evidence is only attached as in-progress evidence with next checks. Direct proof/SMT/CAS artifacts and validation attachments are also checkpointed into the named research session, so later agents can see the exact local evidence and remaining checks. It never executes the queued string through a shell, never uses network access, and does not upgrade trust unless the written or attached artifact satisfies the matching validation gate, verifier route, claim gate, reviewer benchmark gate, or reviewer engine gate.
- When listing saved handoffs in a large workspace, pass `--limit <count>` to CLI `workspace run-nexts` or `limit` to `truth_harness_workspace_run_next_list`. The limit is applied before source-revision/source-snapshot verification, so agents can safely triage the newest packets without turning every resume check into a full history scan.
- Saved run-next list summaries also expose `proofAttemptHistorySummary` when a handoff is repairing a scoped Lean proof obligation. Use it to spot repeated theorem-repair attempts before loading the full packet; the full handoff still carries the complete bounded `proofAttemptHistory` array.
- For supervised autonomous continuation, CLI agents can run `truth-harness workspace pilot-loop <workspace> --source saved-run-next --plan-ref <wrn_id> --json`, and MCP agents can call `truth_harness_workspace_pilot_loop` with `source: "saved-run-next"` and optional `planRef`. If `planRef` is omitted, the loop selects the newest saved handoff whose source revision/snapshot verifies cleanly, or reports why the newest handoff must be refreshed. This mode uses the saved packet as the first structured queue item, not as a shell command: it verifies the handoff source, recreates a bounded run-next plan from the structured item, and stops after that handoff is previewed, executed, blocked, or found stale. Use it when an agent reopens a hard-problem workspace and should attack the exact saved proof blocker instead of inventing a new next step from chat memory.
- Saved report drafts are first-class local handoff artifacts. `truth_harness_report_list` and `truth_harness_report_read` let MCP agents inspect drafts directly with Markdown SHA-256 verification plus `artifactRefs` for the saved JSON sidecar and Markdown sidecar, including file SHA-256, byte size, and copyable citation when the files exist. `truth_harness_workspace_review` also surfaces report drafts as queue items; verified drafts are low-priority review artifacts, while missing or hash-mismatched Markdown becomes a high-priority sharing blocker.
- The repository regression suite builds a golden local workspace through writer APIs and requires `truth_harness_workspace_validate` to pass, so schema, writer, and agent-facing validation drift should fail tests.
- The local schema validator rejects unsupported JSON Schema vocabulary rather than ignoring it; tests scan checked-in schemas to prove their keywords are enforced by the bundled validator.
- `truth_harness_claim_add/list/show/review` records claim lineage and review state. A claim ledger record does not prove the claim; it makes dependencies, superseded mistakes, evidence refs, trust labels, and open checks inspectable. `truth_harness_claim_review` is the agent gate before relying on a claim; non-ready packets should block final wording.
- `truth_harness_literature_log` records local literature/source metadata and review caveats only; it does not call external databases or prove entailment, safety, efficacy, novelty, or patentability.
- `truth_harness_notebook_run_log` records provenance and replay metadata only; it does not execute code, verify outputs, or prove scientific, safety, regulatory, or patent claims.
- `truth_harness_code_sandbox_status` reports whether a measured code-run sandbox is available. `truth_harness_code_run` executes a local command directly without shell interpolation and writes stdout/stderr/exit/policy metadata locally. It is disabled unless the MCP process has `TRUTH_HARNESS_ALLOW_CODE_RUN=1`. Unsandboxed MCP execution is separately disabled unless the process also has `TRUTH_HARNESS_ALLOW_UNSANDBOXED_CODE_RUN=1`; otherwise the agent must set `policy.requireSandbox: true`, which fails closed on native hosts and can pass inside the measured Docker no-network provider. Each call must provide an explicit executable allowlist. The default local policy blocks shell launchers, obvious network clients, destructive commands, package mutations, and git mutations unless explicitly overridden. Execution is async with per-workspace concurrency limits, a 120s timeout cap, and 1 MiB per-stream output caps. Native host code-run records say `networkAccess: unknown`; measured Docker no-network records can say `networkAccess: none`. Both prove only bounded local process execution under the recorded policy, not code correctness, scientific validity, safety, regulatory approval, or patentability.
- `truth_harness_benchmark_run` can write `truth-harness.benchmark-run.v0` records when `write` is true and can mark the MCP call as an error when `failOnFailures` is true; benchmark scores measure system behavior and regression posture, not mathematical, scientific, medical, regulatory, or legal truth by themselves.
- `truth_harness_benchmark_compare` can write `truth-harness.benchmark-comparison.v0` records when `write` is true and can mark the MCP call as an error when `failOnRegression` is true; comparison verdicts flag recorded-run regressions or improvements, not broad model quality or discovery validity.
- `truth_harness_proof_backends` only probes local proof-checker availability. It does not check a proof artifact, does not upload anything, and does not justify a `proved` label without a successful accepted proof-checking run.
- `truth-harness proof project <path>` is a read-only proof-lane inspection. Workspace review and `workspace run-next` use its proof-safety scan to prioritize concrete Lean `sorry`, `admit`, metavariable holes such as `?_` or `?goal`, local `axiom`, and local `constant` blockers before generic proof work. Each blocking marker includes a deterministic `repairTarget` with source SHA-256, marker location, declaration signature hash when available, after-edit commands, and the evidence required before the source can support `proved`; review/run-next handoffs preserve it as `proofRepairTarget`. Treat that repair target as a local work order, not as evidence. When a route already has an open formal-proof obligation with a placeholder Lean source, the same declaration inventory can make the next action concrete by selecting a matching workspace-local theorem/lemma/example and emitting a scoped `truth-harness proof check <file> --declaration <name> --write --route <route_id> --obligation <obl_id> --statement <statement> --statement-hash <hash>` command. A clean scan or selected declaration is still not proof; it only clears the source-placeholder boundary before a real proof-check record is written and attached.
- `truth_harness_proof_check` reads a workspace-local Lean file and runs the configured local Lean command. When `write` is true, it stores a local `truth-harness.proof-check.v0` JSON record plus Markdown report under `.truth-harness/proofs/`, and `truth_harness_proof_list` returns those reusable paths plus route/obligation scope metadata when present. New proof-check records also preserve parser-derived declaration metadata when possible: declaration id, kind, name, source location, signature, signature SHA-256, and source SHA-256. Missing Lean, execution errors, syntax errors, incomplete proofs, and rejected proof attempts return `unverified`; use `failOnUnproved` when an agent must stop unless Lean accepts the artifact. If the proof-check is meant to close a verifier-route formal-proof obligation, pass `routeId` and `obligationId`; unscoped accepted proof-checks remain valid proof artifacts but do not close unrelated route obligations. Rejected or errored scoped attempts are still useful: workspace review can surface the latest failed scoped attempt as the next repair target so agents fix the same Lean file/declaration instead of inventing an unrelated proof. Preserve the declaration target across repairs; if the declaration id or signature hash changes, explain why it still matches the route or validation gate. These repair handoffs expose a structured `proofAttempt` object, a `Lean proof repair artifact` evidence slot, and a `truth-harness route satisfy <route> <obligation> --evidence proof:<proof-check-id-or-path>` attach command placeholder; only use it after the rerun writes an accepted proof-check record for the same scope. Proof-list summaries and workspace review items may include a bounded diagnostic preview from Lean stderr/stdout; use it as a repair clue, not as evidence that the mathematical claim is true or false.
- `truth_harness_smt_backends` only probes local SMT solver availability. It does not check a constraint file, does not upload anything, and does not justify `smt-checked` without a concrete solver run.
- `truth_harness_smt_check` reads a workspace-local SMT-LIB file and runs the configured local Z3 command by default, or cvc5 when `backend: "cvc5"` is selected. When `write` is true, it stores a local `truth-harness.smt-check.v0` JSON record plus Markdown report under `.truth-harness/smt/`, and `truth_harness_smt_list` returns those reusable paths. `truth_harness_smt_solve` first generates a workspace-local `.smt2` source under `.truth-harness/smt/sources/` from explicit integer variables and constraints, then runs the same check workflow. If the SMT-LIB asks for a model and the solver returns `sat`, use the structured `model.bindings` field for follow-up constraints instead of scraping stdout. `sat` and `unsat` can return `smt-checked`; missing solvers, execution errors, `unknown`, and unrecognized output remain `unverified`. SMT evidence can close a generic solver route obligation, but backend-specific obligations require matching backend ids. SMT evidence is not a `proved` label.
- `truth_harness_workspace_snapshot` hashes local workspace artifacts but excludes snapshot files to avoid self-reference; `truth_harness_workspace_snapshot_verify` checks drift, not truth.
- `truth_harness_research_session_start`, `truth_harness_research_session_task_update`, and `truth_harness_research_session_checkpoint` write local runbooks; they organize investigations but do not prove any claim by themselves.
- `truth_harness_expert_review_log` records human review scope and outcomes; it is not proof, medical advice, regulatory approval, or legal advice from the software.
- `truth_harness_vault_seal` requires the vault key in an environment variable and stores encrypted envelopes locally; do not pass vault keys in prompts or tool arguments.
- `truth_harness_vault_verify` decrypts locally but returns only provenance/integrity metadata, not plaintext bytes.
- `truth_harness_evidence_audit` flags evidence posture and overclaim risk; use `writeReport` for human Markdown review packets. It is not proof, medical advice, regulatory approval, or legal advice.
- `truth_harness_validation_plan` turns an audited claim into local validation gates; it is not proof that the gates are satisfied.
- `truth_harness_validation_gate_attach` attaches local evidence to one validation gate. It accepts verifier routes plus validated receipt, proof-check, SMT-check, CAS-check, benchmark-run, source, and literature refs. Exact-computed, cross-checked, SMT-checked, or proved evidence can satisfy a proof gate when scoped to the claim; refuted evidence blocks it; unverified, failed, missing, or unrelated evidence remains open with next checks.
- `truth_harness_model_context_prepare` writes a local pre-flight packet only; it does not call a model, upload data, or prove that the selected context is safe to disclose.
- `truth_harness_disclosure_log` records external context disclosures locally; it does not call the external service itself.
- `truth_harness_simulation_log` records computational evidence locally; it does not imply experimental, clinical, safety, regulatory, or patent validation.
- `truth_harness_experiment_log` records protocol-scoped observations locally; it does not imply safety, efficacy, clinical validity, regulatory approval, or broad real-world truth.
- `truth_harness_claim_chart` records local patent-review structure; it does not determine patentability, novelty, non-obviousness, freedom to operate, inventorship, or filing readiness.
- Do not expose this stdio command through an untrusted remote wrapper.
